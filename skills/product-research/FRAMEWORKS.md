# The PM canon card — read before writing angle 5

Each framework below says **what it is**, **what it predicts** (the question it lets you answer about
*this* decision), **when to use it**, and **the misuse the first scoreboard caught**. Angle 5 picks at
least three that fit the decision, writes the prediction for this case, then says whether the evidence
in section 2 agrees. A framework named without a prediction is decoration.

**Angle-5 table, exactly these columns:**
`| # | Framework · what it predicts here | Evidence (row ids) | Source | Mark | Belief: confirms · contradicts · unknown | Also changes |`
Source is the SOURCES row for the book or page (cite the card itself as `FRAMEWORKS.md`, mark MEDIUM, if no page was opened).

| Framework (source) | What it is | What it predicts here | Use when | Common misuse — don't |
|---|---|---|---|---|
| **Jobs to be Done** (Christensen, *Competing Against Luck*; Ulwick, ODI) | People "hire" a product to make progress in a circumstance | What they fire to hire you; the real competitor may be a spreadsheet or doing nothing | positioning, build-vs-not, "who is this really for" | listing features as jobs; skipping the circumstance |
| **Kano** (Noriaki Kano, 1984) | Customer satisfaction vs. feature presence: basic · performance · delighter · indifferent | Whether shipping it earns anything, or only stops losses | prioritising features users already see in competitors | classifying from how many competitors have it — Kano is measured from *customers'* functional/dysfunctional answers. Never apply it to headlines or positioning copy |
| **The Mom Test** (Rob Fitzpatrick) | An *interview method*: ask about their past behaviour, not your idea | How to get honest evidence from users; why compliments and "I would" are not data | designing the follow-up conversations in the next step | treating it as a theory that predicts market outcomes |
| **Continuous Discovery / Opportunity Solution Tree** (Teresa Torres) | Outcome → opportunities (needs, pains) → solutions → assumption tests, fed by weekly interviews | Whether the solution was chosen before the opportunity was mapped; which assumption to test first | any "should we build X" where X came from a stakeholder | name-dropping it; it is only applied if you place the decision on a tree |
| **The four big risks** (Marty Cagan, *Inspired*; svpg.com/four-big-risks) | **Value** (will *these* customers buy / use it) · **usability** · **feasibility** (can *we* build it: tech, time, data) · **business viability** (does it work for the business: legal, compliance, platform rules, finance, sales) | Which risk is still open; value and business risk first | build decisions, specs | filing legal / platform / privacy rules under feasibility (they are viability) · treating competitors' adoption as retiring *your* value risk (only your customers retire it) · treating all four as equally urgent |
| **Obviously Awesome** (April Dunford) | Positioning = competitive alternatives → unique attributes → value → best-fit customers → market category | Which category frame makes your unique attribute obviously valuable | positioning, landing copy | citing it for a benchmark or a number — it has none |
| **Crossing the Chasm** (Geoffrey Moore) | Early adopters vs. pragmatist majority; win one beachhead segment with the *whole product* | Whether you are selling to visionaries or pragmatists, and what the whole product must include | new markets, launches to a new segment | applying "beachhead" to an existing customer base; reading vendor launches as buyer adoption |
| **RICE** (Intercom) | Reach × Impact × Confidence ÷ Effort | Relative priority, made explicit — especially how low Confidence drags it | comparing two or more options for the same engineers | presenting the score as precision; inventing Reach |
| **North Star / input metrics** (Amplitude playbook) | One metric of delivered value + the inputs that move it | Which input the decision should move, and whether it plausibly can | goal angle (angle 1) | a revenue number as the North Star |
| **Escaping the Build Trap** (Melissa Perri) | Output vs. outcome; product as a value-exchange, not a feature factory | Whether the decision is driven by an outcome or a deadline/story | "build before the round / for the deck" | using it as a slogan |
| **Lean / Build-Measure-Learn** (Eric Ries) | Smallest experiment that tests the riskiest assumption | The cheapest test that would make the decision | when the step is *one named gap* | calling a full build an "MVP" |
| **Heuristic evaluation** (Jakob Nielsen, 1994; nngroup.com/articles/how-to-conduct-a-heuristic-evaluation) | Several evaluators independently judge a design against a written set of heuristics, then consolidate | Whether a design output can be checked against a written standard before users see it — and what that check cannot tell you | design reviews, pre-usability-test checks | treating it as a replacement for user research (NN/g says it is not) · letting evaluators see each other's notes first |
| **Definition of Done / acceptance criteria** (Scrum Guide; Agile practice) | DoD = the quality bar every increment must meet; AC = the conditions one story must meet to be accepted | Whether a written pass/fail standard already exists for the work, so an eval adds cases + a grader + repeat runs rather than a new standard | specs, tickets, release gates | calling AC "evals" when there are no test cases and no one runs them again |

If a decision needs a framework not on this card, name it, cite the book and chapter in SOURCES (mark
HIGH only if you opened a page that states it), and add it here in the same columns.
